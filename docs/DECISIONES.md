# Decisiones y pendientes

Aquí se apunta **qué se ha decidido y por qué**, y lo que queda **pendiente de resolver**. Si una decisión cambia, no se borra: se añade la nueva debajo con su fecha.

## Decisiones

| Fecha | Decisión | Por qué |
|---|---|---|
| 2026-09-17 | Repo **público** en la cuenta personal del lead (`aizetachan`), plan GitHub Free, sin organización y sin licencia por ahora. | En repos públicos la protección de `main` es gratis. Cuando el producto esté construido se decidirá qué hacer con él. |
| 2026-09-17 | **Merge:** toda PR necesita la **aprobación del lead** (validación). Una vez aprobada, **cualquiera del equipo puede hacer el merge**. | El lead valida, pero no debe ser un bloqueo si no está disponible para pulsar el botón. |
| 2026-09-17 | La documentación (`docs/`) la puede aprobar cualquier compañero, no solo el lead. | Que documentar sea ágil y el lead no sea cuello de botella. |
| 2026-09-17 | **Fase 1: el equipo trabaja solo con datos de ejemplo (mocks)**, que se guardan en el navegador. Los emuladores de Firebase los usa solo el lead. | El equipo solo instala Node y pnpm. Cero riesgo de tocar datos reales. La conexión real a Firebase queda escrita y se activa con una variable (`VITE_USE_MOCKS`). |
| 2026-09-17 | Las previews de las PR se construyen **siempre con mocks**. | Hay un único proyecto de Firebase: una preview sin mocks escribiría en los datos reales. |
| 2026-09-17 | Stack: React 19 + TypeScript + Vite + Tailwind v4 + shadcn/ui, React Router, TanStack Query, react-hook-form + zod, sonner. Monorepo con pnpm. | Es lo que shadcn/ui instala hoy por defecto; menos fricción. TanStack Query hace que pasar de mocks a Firebase no toque las pantallas. |
| 2026-09-17 | Diseño: **tema por defecto de shadcn/ui**, sin Figma. Todo el estilo vive en variables CSS en un único archivo. Prohibido escribir colores a mano en los componentes. | Más adelante se abrirá una issue para rediseñar todo; así el rediseño es cambiar un archivo y no se rompe nada. |
| 2026-09-17 | Firebase en **plan gratuito (Spark)**. Proyecto **`finder-lost-found-app`** (nombre visible "Finder"), creado con la cuenta de empresa de Nakamateam. Firestore en `europe-southwest1` (Madrid), con las reglas del repo desplegadas desde el primer momento. | Spark cubre Hosting, previews, Firestore y Auth. Sin cuenta de facturación vinculada no puede haber cargos. La región no se puede cambiar después. |
| 2026-09-17 | Cloud Functions queda como esqueleto (funciona en emuladores, **no se despliega**). El deploy solo publica Hosting y reglas de Firestore. | Desplegar Functions exige el plan de pago (Blaze). |
| 2026-09-17 | Reglas para IAs en **`AGENTS.md`** (fuente única). `CLAUDE.md` solo lo importa. Las reglas críticas se comprueban además con el linter (oxlint, el que trae Vite) y CI. | Que todos trabajen igual usen Claude u otra IA. Lo que bloquea de verdad es el CI, no un archivo de instrucciones. |
| 2026-09-17 | Documentación del proceso publicada con **GitHub Pages** desde `docs/`. Dudas del equipo en **GitHub Discussions**. Tareas en **GitHub Projects**. | Gratis en repos públicos, todo en el mismo sitio, y se edita con el mismo flujo de ramas y PR. |
| 2026-09-17 | La página **`/guia-de-estilos` es temporal**. Está para que el equipo vea de un vistazo los componentes y estilos disponibles mientras arrancamos. Cuando ya no haga falta se elimina (la carpeta `features/styleguide/`, su ruta y el enlace de la cabecera). | Da visibilidad al principio; no es parte del producto. |
| 2026-09-17 | La carpeta **`features/example/` y la página `/ejemplo` son temporales**: son el modelo de cómo se construye una funcionalidad (pedir datos, 4 estados, formulario). Se eliminan cuando el equipo ya tenga pantallas reales que sirvan de referencia. | Referencia para copiar; no es parte del producto. |
| 2026-09-17 | **Una sola fuente de datos de ejemplo**: `packages/shared/src/seed/seed.ts`. Alimenta los mocks y, más adelante, los emuladores. | No mantener dos versiones de los datos falsos. |
| 2026-09-17 | Con datos de ejemplo hay un **selector de persona** en el menú de cuenta (entrar como Lucía, Carlos…) y un botón para restaurar los datos iniciales. | Poder probar la web desde los dos lados: quien publica y quien reclama. |
| 2026-09-17 | El **email no está en el perfil público** (`users`). Quien reclama comparte su contacto al reclamar; quien publicó, solo al aceptar. | Sin Cloud Functions (plan gratuito) las reglas no pueden ocultar campos sueltos; así la privacidad se garantiza solo con reglas. |
| 2026-09-17 | Las fechas se guardan como **texto ISO**, también en Firestore. | Los mismos tipos sirven para mocks y Firebase sin conversiones. |
| 2026-09-17 | La búsqueda por texto se filtra en el navegador. | Firestore no busca texto libre. Suficiente con pocos objetos; cuando crezca hará falta un buscador externo. |
| 2026-09-17 | **Los emuladores de Firebase quedan fuera del día a día**: el equipo no los instala ni los usa, y no hay comando `pnpm emulators`. Se conserva solo la configuración mínima (`firebase.json`, proyecto de mentira `demo-finder`) para la prueba única de reglas y servicios antes de la fase 2. En local la web nunca se conecta al proyecto real. | El equipo trabaja siempre con datos de ejemplo; menos cosas que instalar y que explicar. |
| 2026-09-17 | `functions/` queda **fuera del workspace de pnpm**. | Que el equipo no descargue dependencias que no usa; y el deploy de Functions dentro de un workspace de pnpm da problemas. |
| 2026-09-17 | GitHub se identifica ante Google **sin claves** (Workload Identity Federation), con la cuenta de servicio `github-deploy`, que solo puede publicar Hosting y reglas/índices de Firestore (no lee ni borra datos). Solo este repositorio puede usarla. | La organización de Nakamateam prohíbe crear claves de cuentas de servicio. Además es más seguro: no hay ninguna clave que se pueda filtrar. |
| 2026-09-17 | **Producción también usa datos de ejemplo en la fase 1.** Lo controla la variable `VITE_USE_MOCKS` del repositorio de GitHub (ahora `true`). | Todavía no hay datos reales. Pasar a Firebase será cambiar esa variable a `false`. |
| 2026-09-17 | **Zona protegida:** `.github/` (workflows incluidos), configuración de Firebase, `AGENTS.md`/`CLAUDE.md`/`.claude/`, `components/ui/`, `index.css`, dependencias y configuración de herramientas **no las toca nadie salvo el lead**, ni las IAs. Si hace falta un cambio, se avisa al lead con la issue "Cambio en zona protegida". Tres barreras: la regla en `AGENTS.md`, los permisos de `.claude/settings.json` (bloquean a Claude Code) y CODEOWNERS + aprobación obligatoria del lead (bloquea el merge, use la IA que use). | Un workflow mal tocado puede publicar en producción o romper las previews de todos. |
| 2026-09-17 | **Los datos de ejemplo son la forma permanente de trabajar en pantallas**, también en la fase 2. Ver `ENTORNOS.md`. | El equipo no instala nada más al crecer el producto; pasar a datos reales es cambiar un interruptor. |
| 2026-09-17 | El **enlace de preview vive mientras la PR esté abierta**: caducidad de 30 días (el máximo que permite Firebase) que se renueva con cada cambio subido a la PR, y se borra al cerrarla o fusionarla. | Firebase no permite enlaces de preview sin caducidad; así en la práctica el enlace dura lo que dura la PR y no se acumulan previews viejas. |
| 2026-09-17 | Interfaz y documentación en español; código en inglés. | Convención habitual; evita mezclas. |
